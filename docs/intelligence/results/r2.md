## What the verifier found and fixed

1. **Story tiles downloaded the original photos (4c.5-B3, the main cause of the first-load bytes).** The phase-04c note blamed "six old images without display variants". On the dev data the backfill had already run, and all six had `display_640` and `display_1280`. A DOM probe showed that the six were the story tray cards and the "create story" tile, which still used `useMediaUrl` (the original file) for a 128 × 208 px tile. New `useMediaCover(id, w, h)` and `coverSizes()` in `lib/useMediaList.ts` give these tiles the variants' `srcset`, with `sizes` set to the width the cover crop is drawn at. `StoryTrayCard.vue` and `StoriesRail.vue` use them. First load fell from **2.37 MB to 1.42 MB** on desktop and from 1.98 MB to 1.46 MB on mobile at 3× (target ≤ 1.5 MB). Test: `mediaSrcset.spec.ts` "story tiles (cover crop)".
2. **Old thumbnail rows had a made-up size (4c.5-B3).** Thumbnail rows written before R2 say 320 × 320 whatever the image (for example, 1622 × 1391 → a real 320 × 274 file). The client builds `srcset` from these widths, so they must be real. `media_backfill_display_variants` now reads the real size from the thumbnail object (the object is not rewritten) when a 320 × 320 row cannot be true. It skips re-encoding when only that row was out of date. On dev it fixed 1,172 rows; 190 rows of square images keep a true 320 × 320. A second run does nothing. Test: `test_the_backfill_records_the_real_size_of_an_old_thumbnail_row`.
3. **Deep keyset pages filtered every row above the cursor (4c.8-B3).** The OR filter `t < T OR (t = T AND id < I)` was not an index condition, so page 15 read and discarded about 300 rows. The class now also adds the redundant `t <= T`. On dev, `EXPLAIN ANALYZE` at page 15 shows the index condition `(recipient_id = …) AND (post_created_at <= …)`, and rows removed by the filter went from 300 to 1. Test: `test_a_next_page_range_scans_the_index_from_the_cursor`.
4. **The web still held two delivery constants (4c.2-B3).** The reload-position window (30 min) and the page limit (3 pages) of 08 §7.6 were web literals (`POSITION_SPEC`). They are now config keys `delivery.reload_window_min` (`Int(0, 1440)`) and `delivery.reload_max_pages` (`Int(0, 10)`) on every delivery surface. The web reads them from the server's block and falls back to `SAFE_DEFAULTS`, which a spec keeps equal to the backend defaults; an older server's block without the keys still parses. Tests: `test_delivery_config.py` (keys, values, bounds, required) and `deliveryStore.spec.ts`.
5. **In-flight de-dup ignored per-call headers (4c.8-B3).** Two requests with different `Idempotency-Key` (or any other) headers could share one answer. A request that carries its own headers is never shared now. Test: `apiDedup.spec.ts` "never shares a request that carries its own headers".

No unauthorized content, private-behaviour leak, location data, fabricated count, literal ranking threshold or event outside a transaction was found:
- Snapshot cards draw text and photos only when the server sent them. `snapshot_for` keeps content for public, non-page posts and the viewer's own posts only. A card the batch omits is removed.
- Impressions are sent from visibility only, never on fetch or render. Snapshot cards are skeleton components with no impression tracker.
- `GET /feed/delivery/` is the same for every viewer (401 without a token).
- `entry` is validated and stores nothing.
- The backfill writes no event and no analytics row.

### Notes on the gaps

- **Revised scenario-14 target.** At 400 kbps one KB costs 8 / 400 = 0.02 s. 313.7 KB of critical JS is 6.3 s of transfer before any round trip, so 6 s cannot hold with this JS. The revised target is first post ≤ critical-JS transfer + 3 s, about 9.3 s today. Measured: 12.2 s. On the weak profile the 1.5 s rail hold (`delivery.defer_rails_max_ms`) runs out long before `/feed/` answers, so 23 calls still go out before the first post. Raising it is a config change for the owner; the verifier did not change the default of 08 §7.4.
- **Critical JS.** About 251 KB decoded of the entry chunk is the ar and en message catalogues together. Loading only the active locale saves about 30 KB gzip; even with every known split, about 250 KB would remain. The CI step reports the size without blocking merges until the budget holds. Remove `continue-on-error` when it does.
- **`/media/resolve/` 3-5 calls.** The rounds depend on each other:
  - the viewer's own avatar, at app boot;
  - the hydrated posts' photos and the authors' avatars after `/users/lookup/`;
  - the rails' people and pages after their own lookups.

  The 20 ms window merges each round. Folding them needs the BFF (4c.3b, measure-only in 09).
- **Requests 122.** These are 33 scripts, 34 API calls and about 47 media requests. Fewer scripts depends on the critical-JS work.
- **Mobile timings.** These are under 4× CPU throttling, as 09 requires. The 704 ms baseline was not throttled. Most of the gap is parse and execution of about 1 MB of decoded critical JS.

## Deviations

- **Extra delivery keys.** `defer_rails_max_ms` (Track A) and `reload_window_min` / `reload_max_pages` (verifier) are not in the 08 §7.2 list. They exist so that the web holds no delivery literal (08 §7.4 1.5 s, §7.6 30 min / 3 pages).
- **Video page sizes.** Video uses 20 / 20, not 10 / 20, to keep R1's "video pages full".
- **Legacy cursors.** A cursor issued by the old `CursorPagination` is still accepted for one release (`accept_legacy_cursor`) and continues below its position. Remove it in the next release.
- **Longer-lived photo URLs.** Bucketed display URLs (images, including chat and restricted photos, thumbnails, display sizes and posters) are the same for every authorized viewer within an hour. Each stays valid up to the bucket's end plus 55 minutes, about 2 h at most, against 15 minutes before. A photo removed from a viewer stays loadable from a URL already handed out until then. This follows 08 §7.8 and is noted in `.env_prod.example`.
- **"Before" numbers.** These come from 08 §7.1 and one pre-change run of the web track. A full before run would have needed a second preview server or `git stash`.

## Open items

- **Over target:** critical JS (313.7 KB against 150 KB), mobile first post and first image under 4× CPU, first-load requests (≤ 90), and `/media/resolve/` calls (≤ 2). The next steps:
  - load only the active locale;
  - use the vue-i18n runtime build;
  - make the navbar menus lazy;
  - BFF hydration (4c.3b).
- **Owner choice:** raise `delivery.defer_rails_max_ms` for weak networks, or keep 1.5 s.
- **After the deploy:** run `python manage.py media_backfill_display_variants` once on production media, after the migrations. It is idempotent and writes no events.
- **Not measurable on dev:** `favorites` duplicates (the seeded account has no favorites). The API tests cover it.
- **From the web track:** an untracked file outside the repo's tracked tree may have been changed by one of its commands. The verifier left the untracked design and data folders alone and did not commit them.
