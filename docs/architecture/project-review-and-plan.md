# Tara — مراجعة المشروع وخطة التنفيذ

تاريخ المراجعة: 2026-11-03 · الفرع: `feat/web-social-platform` (commit `29ff7fe` + تعديلات غير مُلتزَمة).

## 1. الخلاصة

المشروع **يشتغل محليًا كنظام كامل**، لكن فقط بعد 6 تعديلات تشغيل، و**لا يمكن نشره حاليًا من clone نظيف**.
الباك إند واسع ومكتمل وظيفيًا إلى حد كبير، والمشكلة في ثلاث مناطق: التغليف والنشر، تكامل الواجهة مع الـ API، وصلابة الأمان والأحداث.
ادعاءات "verified" في تقارير المراحل تعتمد على build وقراءة، وليس تشغيلًا حيًا؛ لذلك ظهرت الأعطال هنا لأول مرة.

| البند | النتيجة |
|---|---|
| الخدمات | 14 خدمة Django + BFF + واجهة Vue (19.3K سطر Python، 8.7K سطر واجهة) |
| الحاويات | 43 حاوية شغالة، 5.7 GB RAM |
| الاختبارات | 116 اختبار عبر 15 خدمة، **كلها نجحت** (بقاعدة بدون migrations، و13 خدمة منها لا تعمل في CI) |
| `vue-tsc` | نجح بدون أخطاء |
| تدفق E2E | تسجيل، تفعيل، دخول، بروفايل، متابعة، صداقة، منشور، Feed، تفاعل، إشعارات، رفع صورة، شات، WebSocket، سوق، بحث: يعمل بعد التعديلات |
| طوابير الأخطاء DLQ | فارغة بعد الاختبار |

### درجة الثقة

- **مؤكد بالتشغيل**: جرى إثباته فعليًا في هذه المراجعة (القسم 2).
- **من قراءة الكود**: بقية البنود، وعددها كبير. مأخوذة من 3 مراجعات مستقلة ولم تُختبر حيًا، وخاصة كل ما يخص Dokploy وK8s؛ لم يُشغَّل أي منهما.
- لم يُشغَّل `ruff` (غير مثبت) ولا `pip-audit` ولا فحص CVE.

## 3. موانع النشر من clone نظيف

تم التأكد من أول بندين وآخرهما مباشرة من git.

| # | المشكلة | الأثر |
|---|---|---|
| D1 | `.gitignore:17` (`lib/`) يتجاهل `frontend/web/src/lib/`؛ 0 من 8 ملفات في git و40 ملفًا تستوردها | الواجهة لا تُبنى من clone نظيف |
| D2 | كل `entrypoint.sh` (14) بصلاحية 644 في git | `permission denied` متوقع على Linux |
| D3 | لا توجد migrations في git لأي خدمة، و`makemigrations` يعمل عند الإقلاع | التحديث الثاني يترك الجداول قديمة، أو crash loop، أو حذف أعمدة عند إعادة التسمية |
| D4 | `EMAIL_HOST: mailpit` ثابت، وSMTP user/password غير مقروءين | لا مستخدم جديد يستطيع الدخول على Dokploy |
| D5 | `environment:` يتغلب على `env_file` | تعليمات `DOKPLOY.md` لتغيير البريد وS3 بلا أثر |
| D6 | لا يوجد `CELERY_TASK_ALWAYS_EAGER` ولا queues منفصلة في Dokploy | معالجة الصور تضيع غالبًا والحالة تبقى `processing` |
| D7 | الـ bucket قابل للقراءة العامة + `/s3/` في nginx معطل | وسائط خاصة مكشوفة، وبروكسي غير صالح |
| D8 | مفتاح `services/identity/.keys-local/jwt_private.pem` غير مُتجاهَل في git ولا Docker | `git add .` يرفع المفتاح، وهو الآن داخل صورة identity المحلية |

## 4. الخطة

التقديرات لمطور واحد متفرغ، وهي تقريبية.

### المرحلة 0 — الأساس والتشغيل بأمر واحد (1–2 يوم)

الهدف: `git clone` ثم `make up` يعمل على أي جهاز.

1. إصلاح `.gitignore` و`.dockerignore` (`/lib/`، `.keys*/`، `.venv*/`، `.env.*`) وإضافة `src/lib/`.
2. حذف `.venv-run` وتجديد مفتاح JWT المحلي.
3. commit لتعديلات `tokens.py` (الـ `roles`) مع اختبارات؛ بدونها كل صلاحيات الأدمن 403.
4. `chmod +x` لكل entrypoints.
5. إصلاح R1 إلى R6 وR16.
6. توليد migrations لكل الخدمات الـ13، وحذف `makemigrations` من الـ entrypoints، وإضافة `makemigrations --check` في CI، وإزالة `--no-migrations` من pytest.
7. Lockfiles بـ `pip-compile` وتثبيت إصدارات الصور.
8. CI: اختبارات كل الخدمات، build لكل الصور والواجهة من clone نظيف، `ruff`.
9. تحديث `README.md` و`docs/README.md` و`Makefile`.

**قبول:** clone جديد على جهاز/مجلد نظيف، `make up`، ثم smoke test ينجح، وCI أخضر.

### المرحلة 1 — استقرار تجربة المستخدم (4–5 أيام)

1. R7–R12 (الشات، البروفايل، الأسماء، الإشعارات، Feed).
2. فقدان البيانات: تعديل منشور من الـ Feed يقص النص إلى 280 حرفًا.
3. تفضيلات الإشعارات: الشكل المرسل غير صحيح وقد يكسر `notify()`.
4. التسجيل: `handle` و`display_name` يُتجاهلان، وحد كلمة المرور 8 مقابل 10.
5. الجلسات: تبويبان يسببان logout، وأي خطأ شبكة يمسح الجلسة، وWS لا يجدد التوكن.
6. Feed: استهلاك `post.deleted` و`post.updated` و`friendship.removed`.
7. إضافة Vitest، وPlaywright لمسارات الدخول والمنشور والشات والرفع، واختبار عقد مقابل OpenAPI.
8. تحويل سكربت الـ smoke إلى اختبار دائم في CI.

**قبول:** Playwright أخضر بالعربية والإنجليزية، ولا UUID ظاهر في الواجهة.

### المرحلة 2 — نشر Dokploy فعلي (4–6 أيام)

1. D4–D7: SMTP حقيقي، متغيرات بدل القيم الثابتة، queues لكل خدمة بدل EAGER.
2. وسائط الإنتاج: توقيع بعنوان عام، بروكسي صحيح، إلغاء القراءة العامة، مواءمة حد 64MB مع 200MB.
3. Endpoint لإعادة إرسال التفعيل، وطريقة لإنشاء أول أدمن.
4. nginx: rate limit، HSTS، CSP، إعادة توجيه HTTP، `X-Forwarded-Proto`.
5. تشغيل `check --deploy` في النشر، وإصلاح `ALLOWED_HOSTS=*` و`AUTO_APPROVE=true` في مولد البيئة، وجعل `DEBUG` الافتراضي False.
6. أسرار لكل خدمة بدل `.env` مشترك، ومستخدم MinIO محدود، وكلمة سر Redis.
7. حدود ذاكرة وتدوير لوج. سيرفر 8GB غير كافٍ عمليًا: الاستهلاك محليًا 5.7GB بلا حمل، فابدأ بـ 12GB على الأقل.
8. نسخ احتياطي لـ Postgres وMinIO ومفاتيح JWT، مع تجربة استعادة فعلية.
9. مراقبة أساسية: تنبيه الـ outbox باسم مقياس صحيح، وAlertmanager.

**قبول:** نشر على سيرفر تجريبي بدومين حقيقي، مستخدم غريب يسجل ويفعّل ويرفع صورة ويدردش، ثم تحديث بتغيير schema بلا فقدان بيانات، ثم استعادة من نسخة احتياطية.

### المرحلة 3 — الأمان والصلاحيات (1–1.5 أسبوع)

1. الرفع: Allowlist، حد حجم فعلي، HEAD + فحص magic bytes، `attachment`.
2. صلاحيات الوسائط حسب السياق (شات، أصدقاء) والتحقق من ملكية `media_ids`.
3. WebSocket: فحص العضوية عند `subscribe`، Origin validation، بدل التوكن في URL، إغلاق عند انتهاء التوكن.
4. الحظر في المجموعات ومحادثات السوق، والتحقق من `reply_to_id`.
5. تنفيذ قرارات الإشراف على المنشورات والـ Feed والبحث، ومنع إعادة نشر الإعلانات المحذوفة.
6. البحث: احترام الخصوصية والحظر، وR13.
7. Refresh token في HttpOnly cookie فقط، وقفل صف عند التدوير، ونافذة سماح قصيرة.
8. Rate limit افتراضي لكل الخدمات، و`NUM_PROXIES`، وقفل حساب عند تكرار الفشل.
9. Idempotency لكل مستخدم، واختراق ميزانية الإعلانات عبر impressions/clicks.
10. مصدر واحد للأدوار: Admin أو claims، مع حذف الآخر، مع اختبارات.
11. مراجعة أمنية أخيرة و`pip-audit`/`npm audit` في CI.

### المرحلة 4 — موثوقية الأحداث (1 أسبوع)

1. Retry مع backoff، ثم DLQ، وأمر replay، وتنبيه على عمق DLQ. حاليًا أول خطأ مؤقت يضيع الحدث نهائيًا.
2. `close_old_connections` في المستهلكين.
3. Publisher confirms و`mandatory`، وتعريف queues قبل النشر.
4. التحقق من إعادة تشغيل RabbitMQ (احتمال توقف outbox دائم، لم يُثبت بعد).
5. لف كل كتابة outbox في `transaction.atomic`، مع assert.
6. إصلاح fan-out: batch بدل صف لكل متابع، وتنظيف outbox وprocessed.
7. اختبارات مباشرة لـ `libs/` (حاليًا صفر).
8. تحديث `04-event-contracts.md` ليطابق الواقع، وحذف أو تنفيذ الأحداث اليتيمة.

### المرحلة 5 — الأداء والجودة (1 أسبوع)

N+1 (خاصة 60 طلب Graph لكل timeline)، pagination للمنشورات والتعليقات والقوائم، ترتيب الـ inbox وقائمة الإشراف، تقسيم `ProfileView.vue` و`PostCard` و`MessagesView`، a11y (dialog، labels، focus)، `dir="auto"` وجمع عربي صحيح، استبدال `alert` برسائل مترجمة، اختبار حمل أساسي.

### المرحلة 6 — الميزات (بعد استقرار ما سبق)

الترتيب حسب القيمة مقابل الجهد:

1. مكتمل في الباك إند وناقص في الواجهة: reactions للرسائل، كتم/تثبيت، جروبات.
2. رسائل صوتية، خصوصية الحقول (يحتاج GET)، هاشتاج ومنشن.
3. Pages (يحتاج list endpoint).
4. مشاركة المنشورات، link preview مع حماية SSRF، الاستطلاعات.
5. Web Push وPWA.
6. لوحة المعلن، ثم feature flags والأدوار.

`docs/architecture/frontend-roadmap.md` قديم: التفعيل، استعادة كلمة السر، الجلسات، تعديل/بلاغ المنشور، وقوائم المتابعين كلها منفذة. يُحدَّث في المرحلة 0.

## 5. قرارات

1. **Kubernetes يتجمد.** الـ manifests لم تعمل على cluster قط، وبها عدة أعطال مؤكدة بالقراءة (NetworkPolicy، probes، أسماء DNS). الهدف الآن Dokploy فقط؛ لا تُصلَّح قبل حاجة حقيقية للتوسع.
2. **لا خدمات جديدة.** الوثائق تقول 17 خدمة، والواقع 14 + BFF. تُحدَّث الوثائق بدل بناء الباقي.
3. **المرحلتان 0 و2 قبل أي ميزة.** لا قيمة لميزات لا يمكن نشرها.
4. **تقسيم الفرع.** الـ commit الحالي 72 ملفًا و+5872 سطرًا. تُفتح PRs صغيرة من الآن، بعد دمجه أولًا مع `main` عقب المرحلة 0.

## 6. المخاطر

- حجم النظام (43 حاوية) مكلف لمطور واحد على سيرفر واحد؛ حدود الذاكرة والمراقبة ضرورية قبل أي مستخدم حقيقي.
- تعديل MinIO: المشروع مبني على الصور الرسمية التي لم تعد متاحة هنا. البدائل تحتاج تقييمًا (نسخة مثبتة موثوقة، أو S3 خارجي مثل Cloudflare R2، وهو الأبسط على Dokploy).
- مراحل الأمان والأحداث تقديراتها الأقل دقة، لأن أغلب بنودها لم تُثبت بعد بالتشغيل.
